THE DEFECT CLASS: "a capability is gated to a hand-maintained per-language list, while the real
behavior is generic — so the two drift, and languages silently get a worse path or a wrong answer."

INSTANCE ALREADY FIXED (for calibration):
`symbolFlowParameterNames` (internal/sem/types.go) used AST parameter names only when
`parameterNamesKnown` was set, and that flag was set in exactly ONE place (parser.go), gated on
`language == "JavaScript" || language == "TypeScript"`. Every other language fell back to a regex
that splits a signature on commas and takes the first token. Consequences, measured:
 - type-first languages got the TYPE as the parameter name (`check(String token)` -> [String]),
   so Java/C#/C/C++/PHP never matched their own params: 7,867 DATA_FLOWS edges missing in
   spring-framework alone.
 - nested punctuation leaked in: Zig `options: struct { scripts: u8, git_commit: u8 }` produced
   params `git_commit` and `}`, fabricating false edges.
There was ALSO a second gate (provider.go entitySymbols) dropping the names on the entity->symbol
copy for non-JS/TS. Fix: read params from the parse tree for any grammar exposing a parameter
list; grammars that expose none report unknown and keep the regex.

CANDIDATE I FOUND (want your verdict + better ideas):
