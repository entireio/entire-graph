## The supermemory model-asymmetry finding
**The mock is ruled out. Which real model it used is unrecoverable. And the canonical spec is probably impossible as written.**

1. The published artifacts are `timings_supermemory_locomo.json` → `locomo_results_20260813_113535.json`, accuracy **77.5974** — this is the banked 77.60. Run window 05:19–11:35 UTC on 2026-08-13.
2. **The mock-backed store did no work during that window.** `boot_sm.sh` (the `OPENAI_MODEL=mock-model` boot) uses `memarms/sm/data`. File-level test over the window: **0 files written in `sm/data`, 23,536 files written in `memarms/smsrv/data`.** I ran this at file level specifically because the subagent's version rested on directory mtime, which would not have proven it. Latency corroborates: `smsrv/server.log` extraction calls cluster **13.2–31.9s**, while all three mock scripts are in-process `http.server` handlers that answer in sub-10ms.
3. **Which real model is unrecoverable.** The run predates env capture — `runmeta.py` was created 6h after the run finished, so `locomo_results_20260813_113535.json` has no model or env field (verified: no env capture in its metadata). No shell history exists on the box. The `smsrv` launch env matches none of the three boot scripts.
4. **`deliverable/FAIR-CONFIG.md:14` claims the canonical spec is `ingest extractor (cognee, letta, graphiti, supermemory) = azure_ai/gpt-5.6-terra`. For supermemory that is unverified — and my measurement today is evidence it is impossible as stated.** Supermemory's server emits OpenAI parameters that this deployment rejects outright. It cannot talk to `gpt-5.6-terra` without request rewriting. So the 77.60 run used something else; the only other real endpoint configured anywhere in the campaign is Fireworks `deepseek-v4-flash`.
