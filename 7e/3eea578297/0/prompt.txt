## Root cause (measured, not guessed)

Two defects compounding, both in shared code:

**1. Connect timeout too tight for a cold-start burst** — `benchmarks/common/llm_client.py::_init_azure_ai` hardcoded `connect=15.0` (also `_init_openai`/`_init_azure` at `10.0`). `LLM_TIMEOUT=600` only sets the *read* timeout, so a 600s budget never applied to connection establishment.

At the start of the question phase `question_semaphore = asyncio.Semaphore(args.question_workers)` (`locomo/run.py:929`) admits exactly N questions at once against an **empty httpx pool**, so all N need a brand-new TCP/TLS connection simultaneously. On this NAT-egressing VM those SYNs get dropped and the kernel retransmits.

Reproduced live on `graphbench-g` (`~/coldstart-diag/diag.py`, 10 concurrent cold calls):
- `connect=15`: 4 OK in ~1s, **6 × `APITimeoutError` at exactly 15.02s, `__cause__ = httpx.ConnectTimeout`**
- `connect=90`: **10/10 OK** — the stalled connects complete at 1s,1s,1s,1s,3s, **20.2s, 20.2s, 36.8s, 36.9s**

So it is not model quality, not retrieval, not the answerer — it is TCP connect. The exception surfaces as `openai.APITimeoutError` with `str()` = `"Request timed out."`, caught by the generic `except Exception` at `_generate_openai`.

**2. Unjittered backoff kept the herd synchronised** — `await asyncio.sleep(2 * (attempt + 1))` (8 sites). All N coroutines fail together, sleep the *identical* interval, wake together and re-issue the identical connect storm. Every attempt fails the same way. `mrq_base` log shows a perfect 10/10/10/10/10 ladder across attempts 1→5, then `return ""`. `locomo/run.py:531` assigns that `""` to `generated_answer`, `:557` records it, judge scores WRONG. First question took 173.66s = 5×15s + (2+4+6+8) backoff + judge's 3×15s + 12s ≈ 173s. Exact match.

**3. (Also fixed) Blank content was never retried** — only `content is None` retried; a `""`/whitespace completion was returned verbatim on the first attempt.

`empty_generated_answers` is only a metric in `~/portwork/score.py:62` — there is **no existing gate**. `full_cmm`/`full_graphify` reported 0 because they got lucky, not because they took a different path.

## Fix

`benchmarks/common/llm_client.py` (shared, backend-agnostic — no backend client touched):
- `_connect_timeout()` — `LLM_CONNECT_TIMEOUT` env, default **60.0**, applied to all three OpenAI-family init paths.
- `_retry_delay(attempt)` — `2*(attempt+1)*uniform(0.5,1.5)`; replaces all 8 fixed sleeps.
- `_generate_openai` / `_generate_anthropic`: blank/whitespace content is now a **retryable failure**, treated exactly like an exception.
- `LLMClient.warmup(concurrency)` — pre-opens `concurrency` pooled connections; best-effort, failures non-fatal.

`benchmarks/locomo/run.py`:
- `await asyncio.gather(answerer.warmup(args.question_workers), judge_llm.warmup(args.question_workers))` immediately after both clients are built, **before any backend work** — identical for every arm.
- Additive `"answer_empty": not generated_answer.strip()` in both cutoff-result dicts.

**Scoring semantics unchanged**: after `max_retries` the call still returns `""`, still gets judged, still scores WRONG, never skipped. Verified by unit test #3/#4. Attempt cap is still 5 (test #5). The only new field is the additive `answer_empty` audit flag.
