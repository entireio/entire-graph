## Review of PR #96 — `fix: stop repository bytes reaching the terminal as control sequences`

Scope: `git diff main...HEAD` (2 commits) plus the uncommitted working-tree changes in `internal/sem/search_closedset.go`, `search_container_map.go`, `search_literals.go` (and untracked `internal/sem/search_blocks_escape_test.go`), which extend the same fix.

The design (guard at the writer, `Line` for one-line records, machine formats untouched) is sound and the core `termsafe` implementation is correct — the CRLF/C1 lookahead, the `escapedAt` width contract shared by scan and rewrite, `Write` returning `len(p)`, and error passthrough all check out. Findings are gaps and one compatibility regression, several verified by running the built binary against purpose-built repositories.

### Findings

**1. `internal/cli/explain.go:194` — high. The `explain` verb still leaks raw ESC to stdout.**
`RenderExplain` output goes straight to `opts.Stdout` with no `termsafe.NewWriter` wrap and no `Line` escaping, while it prints `symbol.FilePath` (a raw Git pathname, explain.go:296) and `symbol.Signature` (a declaration line lifted from source, explain.go:306). Verified end to end: in a repo containing `evil&lt;ESC&gt;[2Kfile.go`, `echo "undefined: Helper" | entire graph explain --repo R --format text` emits byte `033` to stdout — exactly the primitive the PR closes for every other verb. The new sweep `TestNoVerbLeaksControlSequencesToTheTerminal` (termsafe_verbs_test.go:68) does not list `explain`, so nothing catches it. Fix: `out := termsafe.NewWriter(opts.Stdout)` at explain.go:194 (plus `termsafe.Line` on the one-line fields), and add `explain` to the sweep.

**2. `internal/termsafe/termsafe.go:164` — medium. Escaping all of C0 rewrites form feeds in legitimate source, breaking verbatim edit anchors.**
`case character &lt; 0x20 || character == 0x7f` escapes FF (0x0c) and VT (0x0b), which are ordinary page separators in GNU-style C, Emacs Lisp and older Perl/Python sources — not a spoofing primitive (FF just advances the terminal). Verified: a `lib.c` with `\f` page breaks now renders its search snippet as the literal 4-byte `\x0c`. That contradicts the package doc's own invariant ("ordinary output stays BYTE-IDENTICAL … so an agent can copy a snippet verbatim as an edit anchor") — an agent copying that snippet as an `old_string` anchor will fail to match the file, and `TestSearchTextWithoutControlBytesIsUnchanged` uses only clean ASCII so it does not catch this. Suggest passing FF and VT through in `keepLayout` mode (they remain escaped in `Line`).

**3. `internal/sem/search_verify.go:1231` — medium. The VERIFY block's `targets` line is not `Line`-escaped, so a pathname newline forges a line inside the payload.**
`evidenceLine := "  targets " + command.Targets` (and `DerivedFrom` at :1236, `Guard` at :1249) concatenate repository paths into a one-record-per-line block. Verified: a repo containing a file literally named `evil.go\n99. real.go:1 score=99.0 symbol=Fake` produces, in `search --format text`, a correctly defanged result header (`evil.go\x0a99. …`) followed by a VERIFY block that prints the raw newline and a forged second line. The VERIFY block is the one an agent is told to act on, which makes it the worst place to leave the forgery open. Same fix as `searchResultOnOneLine`: `termsafe.Line` on `Targets`, `DerivedFrom`, `Guard`. (`searchVerifyDecorated` at :1230 has the same issue via shell-quoted paths — a literal newline inside the quotes splits the `VERIFY:` record across two lines.)
