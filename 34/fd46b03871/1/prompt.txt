## 5. Adversarial check — the strongest evidence against

**(a) The baseline was not verifying at all on half these instances, and that is where eg's "excess" comes from.**
`javaparser-4538` baseline A = **0**. `lombok-3326` baseline A = **0**. `bat-3108` baseline A = 2 (both rustfmt). `openlibrary` baseline A = 3.
And the reason is a harness artifact:
```
base sharkdp__bat-1892 [9]  cargo build 2&gt;&amp;1 | tail -30
     RESULT:  netjail: no real 'cargo' found on PATH behind the guard.
```
The baseline gave up and hand-rolled `rustc /tmp/mock_check.rs`. The eg agent found `~/.cargo/bin/cargo` and ran the real suite. **A verify verb makes running the suite easy for *both* arms — it would push the baseline's A count up toward eg's, which shrinks nothing and could widen the gap.** This is the single strongest argument against funding.

**(b) The bucket the verb most obviously fixes is a statistical wash.** D: eg 30, base 29, Δ **+1**. You cannot buy back +122 by fixing something the control group pays for equally.

**(c) The agent had a working command and re-ran it anyway — repeatedly, and the cause was not truncation.**
```
bat-3108 eg [34],[35],[46]  identical `cargo test --offline`, three times, three different greps.
                            [35] and [46] both return "74 passed; 0 failed" from a run that already passed.
valkey  eg [40],[42]        identical `./runtest --single unit/cluster/zz-repro-shards --baseport 25500`,
                            twice, differing only in `| tail -45` vs `| grep -E "\[ok\]|\[err\]..."`.
```
Neither result was truncated (2,231 and 943 bytes; 2,161 and 199 bytes). An output *cap* does not prevent a re-run of a run whose output already fit. Only a structured result the agent trusts on first read does — that is a UX claim, not a timeout/cap claim, and it is unverified.

**(d) The one timeout in the corpus is a genuine hang, which a longer timeout does not fix.**
```
bat-1892 eg [55]  cd /tmp/bat_baseline &amp;&amp; ... timeout 900 cargo test --offline ...
                  Exit code 143 — Command timed out after 10m 0s
```
The hanging test is `no_args_doesnt_break` (opens a pty and blocks). The agent's actual fix was `-- --skip no_args_doesnt_break` at idx 59/60. An "ecosystem-aware long timeout for cargo" makes you wait *longer* before learning the same thing. The verb converts 7 polling calls into 1 timeout report — real, but the diagnosis cost remains.

**(e) The verb helps the baseline more than eg on 3 of 8 instances.** E delta is −8 (bat-3108), −11 (lombok); ansible's `run_units.py` is 7 calls in eg vs 9 in base. If the verb suppresses scratch-harness construction uniformly, these three move *against* the eg arm.

**Plain verdict:** the fix is real but small and mis-aimed. It is a **bat-1892-shaped fix**. 14 of the 17 conservative calls come from one instance; drop bat-1892 and conservative addressability falls to **3/122 = 2.5%**. The stated features (timeout, cap, exit code, baseline) target buckets B+C = +31 of +121 (26%), of which only ~7 survive strict scrutiny. The two buckets that actually dominate — A (+30, real iteration) and F (+31, code reading) — are untouched, and E (+26) is 58% one instance's second-checkout expedition.

## Confidence and falsifiers

**Confidence: medium-high on the counts, medium-low on the attribution.**
- Bucket counts: high. Every one of the 763 post-edit tool calls was read; the arithmetic closes exactly (442/321/+121, and the API-call recount hits 370/248/+122 on the nose).
- Addressability: this is a counterfactual on 8 sessions. n=8, and one instance carries 82% of the conservative estimate.

**What would falsify the conservative 14% (raise it):**
1. Run the verb against `sharkdp__bat-1892` and `valkey-io__valkey-790` head-to-head and count actual post-edit calls. If eg's bat-1892 drops below 50 tool calls, my 14 is too low.
2. If the verb turns out to isolate tmpdir + allocate free ports, valkey's 13 D + 14 E calls move in and the conservative figure roughly doubles to ~28%.
3. If a structured pass/fail summary demonstrably stops the re-slice pattern (bat-3108 [35], valkey [42], bat-3108 [42]/[43]), add ~6 calls.

**What would falsify it downward (make the fix look worse):**
1. Re-run the **baseline** arm with the verb available. If baseline's A count rises from 32 toward eg's 62 — which the `netjail: no real 'cargo' found` evidence predicts — the delta does not shrink at all and the net effect could be zero or negative.
2. Check whether the +1.35% is even robust: mean per-instance saving is **−10.52%**, median **−4.16%**. The +1.35% is a total-token number carried by a few large winners. A fix worth +1.3pp on the total is inside the noise of a metric whose per-instance median is negative.
3. Ship the verb and measure lombok-3326. It lost 19.4% with *fewer* post-edit calls than baseline. If instances like it are common in the other 14 losers, the whole turn-count thesis is the wrong lever.

**Recommendation on the funding question:** fund it as a **~+1.3pp headline / ~$1.40-per-8-instances** intervention with a hard prerequisite — measure the baseline arm with the verb enabled too.
