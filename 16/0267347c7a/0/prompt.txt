<result>Findings (2):

**1. `internal/sem/provider_parallel_stream.go:68` — the per-record `workerCtx.Err()` check in the emit callback is now redundant with the `select`/`&lt;-workerCtx.Done()` in `flush`.**

Cost: `workerCtx` is a `*cancelCtx`, whose `Err()` does `c.mu.Lock(); err := c.err; c.mu.Unlock()`. That is a lock/unlock pair on one mutex *shared by all workers*, once per record — ~250k contended lock acquisitions across eight goroutines, in the exact hot path this diff exists to de-cost. It is the last remaining per-record synchronization after the channel send was batched away, so it partially cancels the win the comment above it advertises.

Simpler form: delete the three-line guard and let the callback be `batch = append(batch, value); if len(batch) == providerStreamBatchRecords { flush() }`. Cancellation is still observed once per 256 records by the `select` in `flush`, which drops the batch; the only difference is that a cancelled worker accumulates at most one more partial batch (≤256 records, already inside the documented bound) before `process` returns. Per-record cancellation responsiveness was never real anyway — `process` is what has to notice the context, and it gets `workerCtx` directly.

**2. `internal/sem/provider_parallel_stream.go:60-61` — the `full` temp plus eager re-`make` is a more convoluted spelling of "send, then reset".**

Cost: a reader has to reason about why the reassignment happens *before* the send (it does not need to — nothing touches `batch` during the send, since the callback is only invoked from this same goroutine). It also allocates the replacement buffer even on the cancellation path and on the final flush, where it is immediately garbage.

Simpler form:
```go
flush := func() {
	if len(batch) == 0 {
		return
	}
	select {
	case out.batches &lt;- batch:
	case &lt;-workerCtx.Done():
	}
	batch = make([]T, 0, providerStreamBatchRecords)
}
```
Same semantics, one fewer local, and the "hand off the slice, then start a fresh one" ordering reads in the order it happens.

**Finding 1 — `/Users/evisdrenova/conductor/workspaces/entire-brain/denpasar/.context/entire-graph/internal/sem/provider_parallel_stream.go:68`**
The per-record `workerCtx.Err()` survived the batching rewrite and is now the only per-record synchronization left in the hot path.
Cost: `cancelCtx.Err()` takes `c.mu.Lock()`, and `workerCtx` is a *single* context shared by all 8 workers (created once at line 41), so this is ~250k contended acquisitions of one mutex from 8 cores — ~10-25 ms of lock time plus cacheline ping-pong on exactly the kind of cross-core traffic this diff set out to kill (the comment cites 31% in `pthread_cond_signal`).
Cheaper: check cancellation once per batch instead of once per record — move the check into the `len(batch) == providerStreamBatchRecords` branch (flush already selects on `workerCtx.Done()`, so a cancelled worker still drops out there). 250k checks → ~1k. Same drop-on-cancel semantics, one fewer shared-mutex op per record.

**Finding 2 — `.../provider_parallel_stream.go:61`**
`flush` unconditionally allocates a replacement batch, including on the final flush at line 76, where the goroutine returns immediately after and the buffer is never written.
Cost: one dead 48 KB zeroed large allocation per file = ~2000 × 48 KB ≈ **96 MB of allocate-and-discard per run**, ~40% of this function's total churn. The eager `make` at line 55 adds the same waste for every file that emits zero relations (inventory-only/unparseable files, of which there are many in a 2k-file tree).
Cheaper: `batch = nil` in `flush`, and allocate in the emit closure on first append (`if batch == nil { batch = make([]T, 0, providerStreamBatchRecords) }`). Deletes both the final-flush buffer and the zero-record-file buffer; no API or ordering change.

**Finding 3 — `.../provider_parallel_stream.go:55` and `:61` (lower confidence, biggest ceiling)**
Every batch is freshly allocated even though the consumer is its exclusive owner the moment the loop at line 102-106 finishes.
Cost: ~5000 allocations/run (2000 eager + ~1000 full-batch refills + ~2000 final flushes) × 48 KB ≈ **240 MB zeroed per snapshot**, all on the large-object path. That's roughly 25-40 ms of memset, ~5-10 ms of mheap allocation, and 1-2 extra GC cycles — call it 50-150 ms, low single-digit percent of a multi-second 2k-file snapshot. Also note the fixed 256 cap is oversized for the median file (250k/2k ≈ 125 records), so ~half of each eager buffer is zeroed and never touched.
